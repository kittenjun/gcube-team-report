1. API Gateway 기반 API 공개 및 인증 체계 정립

기간: 1~1.5개월

주요 추진 내용

  • 기존 플랫폼 API의 외부 공개 범위 및 접근 권한 정책 정의

  • API Gateway를 통한 API별 권한, 호출 범위 및 접근 제어 적용

  • 외부 사용자·시스템 인증과 내부 플랫폼 인증 체계 분리

  • 외부 인증정보를 내부 사용자 및 권한 체계와 연계

  • API Key, Token, Rate Limit 등 외부 연동을 위한 공통 보안 정책 정립

목표

  • 기존 API를 외부 서비스 및 개발 도구에서 안전하게 활용할 수 있는 공개 체계 마련

  • 외부 인증과 내부 인증을 분리하여 플랫폼 내부 보안 구조와 서비스 독립성 확보

2. 플랫폼 아키텍처 재정립 및 개발 체계 표준화

기간: 4개월

주요 추진 내용

  • 비대해진 API를 PC방, EDU, 한자연 등 업무 도메인 단위로 1차 분리

  • 각 도메인 내부 기능을 책임과 역할에 따라 서비스 단위로 재분리

  • API Gateway를 중심으로 서비스 간 통신 구조 표준화

  • 서비스별 데이터 영역 및 DB 분리 기준 수립

  • API, Billing, Alarm, Task, Event 등 플랫폼 구성요소 간 역할과 책임 재정립

  • 서비스별 프로젝트 규모를 축소하여 독립적인 개발·배포가 가능한 MSA 구조로 전환

  • 공통 개발 규칙, API 규격, 프로젝트 구조 및 문서화 기준 정립

통합 테스트 체계 및 Test Tool 구축

  • GCUBE 플랫폼 및 PC방, EDU 등 확장 서비스에 대한 공통 Test Tool 개발

  • 서비스 배포 전 API 및 주요 기능에 대한 사전 검증 체계 구축

  • 서비스 간 연계 및 전체 시나리오에 대한 통합 테스트 지원

  • 반복 가능한 테스트 시나리오 및 결과 관리 체계 마련

  • 향후 신규 서비스에도 동일한 테스트 체계를 적용할 수 있도록 표준화

AI Agent 기반 개발 체계 정립

  • 소규모 서비스 단위로 AI Agent가 분석·개발·테스트할 수 있는 프로젝트 구조 마련

  • 개발 규칙, API 명세, 테스트 시나리오 등 AI Agent가 활용할 표준 개발 정보 정립

  • Test Tool과 연계하여 AI Agent 개발 결과를 자동 검증할 수 있는 체계 마련

목표

  • 플랫폼 복잡도 및 서비스 간 결합도 감소

  • 서비스별 독립적인 개발·배포·검증 체계 확보

  • GCUBE 및 확장 서비스의 사전·통합 테스트 표준화

  • AI Agent를 활용한 개발부터 테스트까지 일관된 개발 체계 마련

3. TS 및 영업 요구사항 서비스화

기간: 4개월

연구소 및 선행 개발 결과를 기반으로 GCUBE 플랫폼에 통합하고, 실제 사용자 환경에서 사용할 수 있는 서비스 형태로 전환합니다.

추진 순서

1) Instance 서비스

  • 김성구 책임의 GCUBE 플랫폼 선행 작업을 기반으로 연계

  • PC방 Agent에 Instance 실행 및 제어 기능 추가

  • Instance 생성·관리 기능을 GCUBE Console에 적용

  • PC방 GPU 자원을 Instance 형태로 제공할 수 있는 서비스 구조 완성

2) R2 Storage 및 Snapshot

  • 권봉재 실장이 개발한 Backend API를 기반으로 GCUBE 플랫폼 연계

  • R2 Storage 기능을 GCUBE Console 및 CLI에 적용

  • Snapshot API 제공 이후 생성·복원 기능 추가 연계

3) Auto Scaling

  • 선행 기술 검증 결과를 기반으로 GCUBE 환경에 적용

  • 자원 상태 및 사용량에 따른 자동 확장·축소 정책 서비스화

4) GPU Orchestration

  • 연구소 선행 기술을 기반으로 GCUBE 자원 관리 체계에 통합

  • TS 요구사항을 실제 운영 가능한 플랫폼 기능으로 서비스화

목표

  • 선행 개발 결과를 GCUBE Console, CLI, Agent 등 실제 서비스 영역까지 연결

  • 연구소 기술과 플랫폼 개발 간 서비스화 절차 정립

  • TS 및 영업 요구사항을 플랫폼의 지속 가능한 공통 기능으로 내재화

4. 이슈 및 협의 필요 사항

  • 시공간분석플랫폼 인수 테스트 및 인계

    • 인수 범위, 테스트 기준, 잔여 이슈 및 운영 인계 일정 확정 필요

  • 과제 및 타 프로젝트 담당자 부재 가능성

    • 담당자 부재 시 일정 지연과 기술 공백이 발생할 수 있으므로 백업 담당자 및 인수인계 체계 마련 필요

  • 병행 과제 간 우선순위 및 인력 배분

    • 아키텍처 개선과 신규 서비스 개발이 동시에 진행되는 만큼 핵심 인력의 투입 우선순위 확정 필요
